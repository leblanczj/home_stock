# 实现提示词：家庭日用品库存 Android 应用

把下面从「你要做的事」到文末整段复制给实现用的 AI。不要再让它写一份设计，直接做出能安装运行的应用。

---

你要做的事：在一个空的 Android 工程里实现「家庭日用品库存」手机应用，并让它真正可运行。直接写代码、界面和测试。不要再输出一份设计文档来代替应用，不要留空页面，不要用假数据充页面。

这是单用户、一部手机、本地优先。不要账号，不要登录，不要后端，不要网络同步，不要你自己发明的服务器。卸载前数据只在这台设备上。

## 技术栈（锁定）

- Kotlin
- Jetpack Compose
- Material 3
- Room
- 购买截图存在应用私有目录
- minSdk 26
- 使用当前稳定的 Compose、Room、Kotlin 版本
- 界面文案用中文
- 领域计算（库存重放、速度、预计用完、提醒判定）写成不依赖界面的纯 Kotlin，并用 JVM 单元测试覆盖下文的验收数据。禁止只用二进制浮点做金额和数量加减

金额用人民币「分」（整数）。数量内部用毫单位（1 个单位 = 1000，整数），界面最多显示三位小数。

可以按你习惯拆模块，但计算必须能不启动模拟器就测。

## 产品范围

用户记录家里的日用品、购买价格和截图，记下使用，估计还要多久用完，并单独看哪些批次快过期。

可以有多个住所。每个住所的用品、批次、库存和速度完全分开，列表里永远不要混在一起。不要做库存调拨，也不要在切换住所时自动搬库存。

底部三个入口：首页、临期、住所。

- 首页：列出当前查看的住所里快用完的用品（在手、速度、预计何时用完），提供新购 / 点数 / 消耗 / 废弃，并能进入全部库存
- 库存列表：该住所全部用品，进入用品详情
- 用品详情：速度、预计用完、两个提醒天数、价格图、批次、记账入口
- 临期：该住所快过期的批次
- 住所：新增、删除、为一段时间设置住所和人数

顶栏可以切换「正在查看的住所」。这只切换列表，不修改当前生效的居住区间。

## 必须遵守的计算规则

### 点数（盘点）

界面按钮写「点数」。它的含义是盘点。

- 用户输入实盘数量，应用把在手改成这个数
- 它不是新购，也不是用户手填的一笔消耗
- 账面 = 重放完这次盘点之前的在手。账面已经包含上次结存以来的新购、显式消耗和废弃
- 推算消耗 = max(0, 账面 − 实盘)。这笔是真实消耗，计入周、月、年速度
- 盈余 = max(0, 实盘 − 账面)。盈余是调整，不是负消耗，不计入速度，不进入价格图
- 推算消耗和盈余不会同时大于 0
- 显式消耗功能保留。同一批货不能算两次：显式消耗已经减少账面，推算消耗只包含还没记过的缺口
- 提交前给用户看预览：差额是推算消耗、盈余，还是没有变化

推算消耗大于 0 时，按先到期先出从批次扣减，使剩余之和等于实盘。

盈余大于 0 时，新建来源为「盘点盈余」的批次：数量等于盈余，没有购买价格、优惠、渠道、到期日、截图。

推算消耗的时间归属：

- 基准时刻 = 上一笔盘点的时刻；若没有，则是该用品第一笔新购的时刻
- 把数量均匀分到 (基准时刻, 本次盘点时刻]
- 只把落在本用品所属住所的居住区间上的部分，计入对应人数。人数中途变过，就按各段时长拆开
- 其他住所或没有居住区间的时间，对应数量记为未归属：库存已按实盘改掉，但不进入任何速度。不要把这部分除以人数，不要记到别的住所
- 时长为 0 时，盘点时刻落在本住所的居住区间上，就全部计入那个情况；否则未归属
- 用毫单位，最后一段加上余数，各段之和等于推算消耗

### 速度

一个情况 = 住所 + 人数。只统计这个情况下的显式消耗和分摊到的推算消耗。

不要算「总消耗除以人数」。不要在某个情况没有记录时借用另一个人数的速度。

废弃不计入速度。盈余不计入速度。新购不计入速度。

窗口是滚动时长，半开区间 [现在 − D, 现在)：

- 周：D = 7 天
- 月：D = 30 天
- 年：D = 365 天

全应用只有一个预测窗口设置，默认月。用品详情展示三个窗口。选中的那个标「预测依据」，另外两个标「参考」。预计用完日只由选中的窗口决定。

日速度的分母是这个情况在该窗口内的生效天数，不是 7/30/365 整个窗口，也不是人数。窗口的作用是只采用最近 7/30/365 天里的生效时间和消耗。

判定：

- 该情况从未有过大于 0 的显式消耗或推算消耗：速度未知
- 窗口内生效时长为 0：不适用（不要显示成速度 0）
- 生效时长大于 0、窗口内消耗为 0、但以前有过消耗：速度 0
- 否则：日速度 = 窗口内消耗量 / 生效天数

预计用完：

- 速度未知或不适用：没有预计用完日
- 速度 0：文案说明当前窗口没有消耗，不估日期
- 速度大于 0：预计天数 = 在手 / 日速度，用完时刻 = 现在 + 预计天数

查看某住所时：若该住所正是现在生效的住所，用现在这段的人数；否则用该住所最近一段居住区间的人数。那个情况没有消耗历史就显示未知。

居住区间以后被补上或改过，速度要重算。

### 先到期先出

消耗、废弃、盘点推算消耗，都从剩余大于 0 的批次扣：到期日早的优先；没有到期日的最后；到期日相同则更早购入的优先。

库存不足时拒绝消耗和废弃，不能出现负库存。

### 价格

实付单价 = (购买价格 − 优惠金额) / 数量。

购买价格是优惠前总价，不是单价。价格图的纵轴是实付单价，横轴是购买时间。只有新购批次进入价格图。盘点盈余不进入。

同一住所、品牌和规格相同（去掉首尾空白）的新购并入同一个用品。另一个住所即使品牌规格相同，也是另一个用品、另一张图、另一套库存。

选中一个或多个购买点后，每个点显示：购买数量、优惠金额、购买价格、实付单价、渠道，并能打开这一笔的截图。

### 提醒（两个默认值都不要改错）

每个用品有两个独立设置：

- 快用完天数，新建时默认 **5**。首页只用这个数
- 快过期天数，新建时默认 **3**。临期页只用这个数

允许用户改成 0 到 365 的整数。0 表示只提醒已经用完，或到期日就是今天及更早。

快用完（用品，出现在首页）满足任一：

- 在手为 0
- 预测日速度大于 0，且预计天数 ≤ 该用品的快用完天数

速度未知且在手大于 0：不进首页。

快过期（批次，出现在临期页）同时满足：

- 剩余大于 0
- 有到期日
- 到期日 ≤ 今天 + 该用品的快过期天数

已过期会满足第三条。没有到期日的永不出现。剩余为 0 的不出现。

不要把默认值做成 14 天或 30 天。不要用一个全局阈值覆盖用品自己的设置。不要因为快过期就把用品放进首页，也不要因为快用完就把批次放进临期页。

### 居住区间

一段时间里只有一个住所、一个人数。区间含起点、不含终点。任意两段不能重叠；重叠时保存失败，指出冲突的那段，不要自动改旧数据。首尾相接可以。

提供快速设置：住所、人数（≥ 1 的整数）、开始、结束（结束可为「至今」）。

提供「从现在起改为……」：结束当前区间并开始新区间。两步是一次事务，失败则全部回滚。这个操作不移动库存。

没有居住区间时仍可记账。那些消耗在速度里未归属，并提示用户补区间。

### 删除住所

必须确认。确认框写明用品数、批次数、截图数，以及历史会被永久删除、库存不会转到别的住所。取消则不删。确认后删除该住所的用品、批次、事件、区间和照片文件。不要自动激活另一个住所。

## 数据与重放

用 Room 保存住所、居住区间、用品、批次、截图索引、记账事件、事件的批次扣减、应用设置。

在手和速度由事件按时间重放得到，不要只改一个无法回溯的库存数字。同一时刻的顺序：新购、废弃、显式消耗、盘点，然后是保存顺序。

新购保存后，数量不可改。购买价格、优惠、渠道、到期日和截图可以改。消耗、废弃、盘点、新购可以删除。删除或修改后整段重放。若重放会导致某笔扣减超过当时库存，拒绝并告诉用户是哪笔挡住了。

用品字段至少包括：住所、品牌、规格、单位、快用完天数、快过期天数。

批次至少包括：用品、来源（新购或盘点盈余）、时刻、原始数量、剩余、价格（分，可空）、优惠（分，可空）、渠道（可空）、到期日（可空）。

事件要能重算出每一次盘点的账面、推算消耗和盈余。

## 照片

用户从相册选择一张或多张图片。选择后立刻复制到应用私有目录，例如 `filesDir/purchase_photos/<批次id>/<图片id>.jpg`。Room 只存相对路径。以后不要依赖相册原 URI。

截图只属于那一笔新购。用品详情的价格历史里，选中购买点后可以打开。多张可以切换。文件丢失时显示「截图文件丢失」，不要崩溃。删除批次或住所时删除文件。

不要上传。不要申请不必要的网络权限。

## 界面行为

- Material 3，跟随系统深浅色
- 首页快用完一行要有：名称、在手、预测窗口的日速度、另外两个参考速度、预计用完时间、该用品的快用完天数
- 排序：在手为 0 在前，然后按预计天数从短到长
- 临期一行要有：名称、剩余、到期日、已过期几天或还要几天、渠道、该用品的快过期天数
- 排序：已过期在前，然后按到期日
- 价格图支持多选。未选中时提示点选。选中项按时间列出上文规定的字段
- 没有购买时，图的位置是空状态「还没有购买记录」
- 没有住所、没有用品、没有快用完、没有临期、速度未知，都要有明确中文说明，不要留白屏
- 新购表单实时显示实付单价
- 点数表单显示账面，并在提交前显示推算消耗或盈余
- 消耗若落在本住所居住区间之外，先警告：库存会减少，但这笔不进入速度
- 校验失败时用中文说明原因：数量、优惠大于总价、渠道为空、库存不足、区间重叠

空状态文案要能让人知道下一步去哪：建住所、设置人数、记一笔新购。不要预置示例用品。

提醒只做应用内列表。不要系统通知，不要桌面小组件，不要条码扫描，不要分享，不要登录。

## 数值验收（做成单元测试）

把「现在」固定为 2026-05-01 00:00。用这些数据断言，不要只做近似的界面演示。

住所「家」。用品清风 / 130抽×6 / 提。快用完天数 5，快过期天数 3。预测窗口为月。

居住区间：

- 家，2 人，[2026-04-01 00:00, 2026-04-11 00:00)
- 家，4 人，[2026-04-11 00:00, 2026-05-01 00:00)

事件：

1. 2026-04-01 00:00 新购 10。购买价格 10000 分，优惠 1000 分，渠道超市，到期 2026-06-30。实付单价 = 9 元/提
2. 2026-04-05 显式消耗 2
3. 2026-04-08 废弃 1
4. 2026-04-10 盘点实盘 5。断言账面是 7，推算消耗是 2，盈余是 0
5. 2026-04-20 新购 6。购买价格 6600 分，优惠 600 分，渠道线上，到期 2026-05-03。实付单价 = 10 元/提
6. 2026-04-25 显式消耗 3。断言先扣到期 2026-05-03 的批次
7. 2026-04-30 盘点实盘 10。断言账面是 8，推算消耗是 0，盈余是 2

然后断言：

- 在手为 10。其中 06-30 到期的剩余 5，05-03 到期的剩余 3，盈余批次剩余 2
- 家·2人的消耗合计是 4，不是 6。废弃的 1 和已经记过的显式消耗 2 都没有被再加进推算消耗
- 家·2人：周速度不适用；月速度和年速度都是 0.4 提/天（4 提 / 10 天）
- 家·4人：周速度是 3/7 提/天；月速度和年速度都是 0.15 提/天（3 提 / 20 天）。分母不是 30，也不是人数 4
- 预测用月速度。预计用完时刻是 2026-07-06 16:00（10 / 0.15 天 = 66 天 16 小时）
- 该用品不在快用完列表（66 天多 > 5，且在手不为 0）
- 把该用品快用完天数改为 80 后，它进入快用完列表；改回去后退出。这不改变临期结果
- 到期 2026-05-03 且剩余 3 的批次在临期列表中；06-30 的批次不在；盈余批次不在
- 把快过期天数改为 1 后，05-03 的批次退出临期列表。这不改变快用完结果
- 价格图只有两个点，9 元和 10 元。盈余批次不在图上
- 另造一个当前日速度为 1、在手为 2 的用品：预计 2 天，默认 5 天时在快用完列表；阈值改为 1 后不在；在手改为 0 后即使速度未知也在
- 另造一个昨天到期且仍有剩余的批次：即使快过期天数是 0 或 1，也在临期列表
- 先有显式消耗、再盘点出额外缺口时，速度里的数量等于显式加推算，等于实物缺口减去废弃，不会把显式消耗再加一次
- 实盘高于账面时，速度不因为这笔盘点变小
- 为「家 · 2人」没有消耗、但「家 · 4人」有消耗的用品做预测时，若当前人数是 2，速度必须是未知，不能显示成 4 人速度或 4 人速度除以人数

再断言这些失败路径：

- 消耗大于在手被拒绝
- 优惠大于购买价格被拒绝
- 居住区间重叠被拒绝，旧数据不变
- 删除住所在确认前数据还在
